# 标书 Agent 细节质量优化方案

版本：2026-10-24  
依据：真实项目 `f442cd53594a2878ccb46731` 十步回放、最终 DOCX/XLSX/PDF、阶段校验记录

## 一、核心判断

当前系统已经解决“十步可以连续执行、文件可以生成、过程可恢复、产物可追溯”的问题，但尚未解决“标书内容达到专业人员可直接审核的质量”。根因不在单个模型，而在验收口径：现有 `passed` 主要代表阶段产物存在且结构一致，没有充分覆盖内容正确性、证据适用性、响应针对性和已知字段完整性。

必须把以下状态分开：

1. `executed`：任务已执行，文件已产生。
2. `structure_passed`：结构、格式、哈希和页数通过。
3. `content_passed`：字段、语义、证据和交叉关系通过。
4. `human_approved`：需要业务判断的事实已确认。
5. `delivery_ready`：资格、报价、签章、时点材料和递交规则全部通过。

十步全部执行完成不再自动等同于十步内容通过。

## 二、本次项目暴露的具体问题

### 1. 已知字段没有进入正文

项目名称、项目编号、投标人等事实已经在项目对象和输入文件中存在，但投标函、报价表、封面仍有空字段。当前校验把这些空值并入 `source_missing`，没有识别“系统已知但未写入”。

### 2. 技术要求拆分粒度不稳定

货物需求一览表被合并为一条，并被归入“充换电子系统/充电设备”，实际同时包含三类车辆、充电桩和备品备件。分类通过了结构校验，但业务语义错误。

### 3. 响应存在复述代替回答

部分“投标人响应”只是把招标原文改成“将保证”“将予以配合”，随后判定“无偏离”。这只能证明文本被处理，不能证明车辆、部件、服务或承诺真实满足。

### 4. 比较对象错位

部分要求是“参考型号/自动挡”，响应却引用变速箱结构并直接判定负偏离；部分尺寸、续航、电池能量等行混用历史标准答案、检验报告现值和本项目拟供配置，没有明确区分“历史值、原件实测值、本次承诺值”。

### 5. 证据位置没有闭环

资格项虽然标记为 `met`，但 `actual_location` 为空。系统知道使用了证书或报告，却没有形成“文件—页码—字段/区域—支持结论”的可点击证据坐标。

### 6. 权威库召回策略过于二元

目前偏向“同车型精确命中，否则留空”。这能防止串车型，但没有处理型号别名、报告锁定子型号、同一证据多种写法和同部件同参数的可证明继承关系，造成该复用的内容没有复用。

### 7. 视觉检查与内容检查脱节

第十步能识别方向、裁切、空白和页序，却不能发现“已知字段为空”“无偏离缺证据”“引用页不支持结论”“响应回答了另一个参数”等内容问题。

### 8. 构建脚本项目化过强

若阶段脚本写死项目路径、输出名、页码或特定证件修复规则，当前项目能通过，换项目后会失效。项目特例应成为数据规则或修复记录，不应沉入通用引擎。

## 三、目标架构

建立六个互相独立、可审计的数据层：

1. **招标要求层**：原文、编号、物理页、要求对象、比较运算符、单位、阈值、强制性、评分关系。
2. **企业事实层**：企业、车型、部件、证书、业绩、财务等事实及原件坐标。
3. **历史标准答案层**：车型、子型号、适用范围、历史原文、来源项目和版本。
4. **本项目决策层**：拟供型号、承诺值、报价、人员、偏离处理、人工批准状态。
5. **文档装配层**：字段和章节只消费已经批准的数据，不自行推断业务事实。
6. **审核层**：规则检查、语义检查、证据检查、视觉检查分别出结论。

模型只负责语义理解、候选匹配和正文表达。数值比较、单位换算、字段回填、证据坐标、版本依赖和通过门禁由确定性规则控制。

### 技术响应表的明确交付边界（2026-10-24确认）

- Agent只生成完整的八列内部核对表：车型、子系统模块、部件模块、功能模块、标准车型答案（历史投标响应）、本次招标要求、投标人响应、偏离说明。
- 八列表必须包含总则、标准规范、通用技术要求、技术参数、备品备件、试验检验、验收、技术服务培训、技术资料、包装运输和其他全部技术要求，不能只输出车辆参数。
- 八列表中的投标人响应和偏离说明是供业务人工修改核对的候选内容。Agent不执行业务内部核对，也不授予“内部核对通过”。
- 三列正式表不是Agent在本阶段的输出。只有业务人工完成八列表修改核对后，才可由已核对版本派生“本次招标要求／投标人响应／偏离说明”三列并装入标书。
- 未经业务人工核对的八列表及其三列投影均不得进入标书正文。

## 四、十步流程的改造重点

### 第一步：原件建档

- 对原件按内容哈希去重，保留文件名别名。
- 检查 PDF/DOCX/XLSX 的可读页、文字层、扫描页、表格和图片。
- 建立 `document_id + page + region` 坐标，后续引用不再只写文件名。
- 通过条件：所有输入可读、角色明确、版本唯一；不评价业务满足性。

### 第二步：招标解析

- 将要求拆成“一个对象、一个参数、一个判断”的原子条款。
- 货物清单按车型/设备/备件分别建立采购对象，不合并成一条技术响应。
- 自动提取运算符：`≥、≤、范围、必须、提供、承诺、不得`。
- 建立资格、评分、技术、商务、合同和递交六类关系图。
- 通过条件：原文覆盖率 100%，原子化抽检通过率 100%，每条均有物理页引用。

### 第三步：骨架与字段契约

- 每个空位增加字段类型：已知事实、业务输入、签章动作、证明附件、受保护空白。
- 每个字段声明来源优先级和是否允许为空。
- 系统已知字段为空时直接失败，不能归入 `source_missing`。
- 通过条件：招标要求到章节/字段覆盖率 100%，必填字段规则完整。

### 第四至六步：资料与证据

- 建立车型、子型号、部件、证书之间的实体关系，不靠文件名猜测。
- 每条证据生成“支持什么、不支持什么、有效期、持证主体、型号范围”。
- 资格结论必须带 `document_id/page/region/quote_or_field`。
- 没找到证据时保存完整检索日志；找到近似资料不得自动视为满足。
- 通过条件：所有 `met` 必须能一键定位原件，证据主体、型号、时点和参数均一致。

### 第七步：技术响应

- 先识别要求类型：数值、枚举、范围、功能、材料、标准、服务、承诺、证明文件。
- 数值要求用比较器计算偏离，统一单位后再判断。
- 响应必须包含：本次拟供值、比较结论、证据、适用车型；不能只复述原文。
- 明确分开三列事实：历史标准答案、原件当前值、本项目承诺值。
- 历史库检索分四级：同型号同子型号、同型号可证明版本、同部件同证据、仅供措辞参考。只有前两级可自动进入事实列。
- 通过条件：逐行语义同题、车型一致、数值可计算、结论可追溯；无证据的“无偏离”一律拦截。

### 第八步：内容审核

- 增加“回答是否针对问题”的语义审核。
- 增加“结论是否被证据支持”的证据审核。
- 增加“已知字段是否遗漏”的字段审核。
- 增加“同一事实跨 DOCX/XLSX/证书是否一致”的交叉审核。
- 将审核结果分为错误、业务缺项、需人工判断、格式问题，不再混为 `open_items`。

### 第九步：组装

- 组装器只能读取已验证的数据对象，不在装配时生成新事实。
- 原件装配按证据引用自动生成附件索引和正文交叉引用。
- 项目路径、文件名和特殊修复全部参数化。
- 输出目录仍只保留 DOCX、内部 XLSX、预览 PDF。

### 第十步：终审

- 视觉审查继续检查页序、裁切、方向、表格、目录和清晰度。
- 同时运行最终内容门禁：必填字段、证据引用、负偏离、资格、报价、签章和时点材料。
- 修改后根据依赖图只重跑受影响步骤，并对分页影响范围重新渲染检查。
- `delivery_ready` 只能由独立门禁计算，任何阶段或模型不能自行赋值。

## 五、知识库与检索体系

### 1. 企业知识库

保存企业原件及解析字段。每条事实必须绑定原件，不保存模型推断为事实。

### 2. 历史响应权威库

保存已经人工核验的标准答案，并增加：车型、子型号、部件、参数、适用范围、来源项目、审核人、版本、失效原因。

### 3. 检验报告参数库

将报告中的型号、参数、单位、测试条件和页码结构化。技术响应先查此库，再回看原页。

### 4. 检索流水线

`实体过滤 → 关键词/BM25 → 向量召回 → rerank → 规则校验 → 原页验证`

rerank 只能改善候选排序，不能替代车型、主体、有效期和数值规则。WeKnora可承担原件解析和候选召回，最终适用性仍由本系统规则和 Agent 审核决定。

## 六、工作台应增加的审核界面

1. **项目事实页**：展示已知值、来源和待业务输入，允许逐项批准。
2. **资格证据页**：每项资格并排显示招标原文、系统结论和原件页。
3. **技术逐条页**：显示招标要求、历史答案、原件值、本次承诺、证据和偏离。
4. **评分策划页**：显示可得分、缺证据、拟放弃分值及补料动作。
5. **异常中心**：只展示系统无法决定或相互冲突的项目，减少人工浏览量。
6. **最终放行页**：报价、保证金、授权、签章、动态查询和负偏离逐项确认。

## 八、实施顺序

### P0：先修正确性门禁

1. 重定义阶段状态和 `passed` 含义。
2. 增加已知字段漏填检查。
3. 资格和无偏离结论强制绑定证据坐标。
4. 重做技术条款原子化、数值比较和同题审核。
5. 用本次项目建立字段级黄金标准。

P0完成前，不继续扩充模型列表或增加更多自动续跑轮次。

### P1：重构知识与检索

1. 建立企业事实、车型、报告、历史答案实体关系。
2. 配置向量召回和 rerank，但保留规则过滤。
3. 建立型号别名和可证明继承规则。
4. 为原件生成页级、字段级引用。

### P2：重构生成和审核

1. 技术响应改为结构化事实生成正文。
2. 增加证据审核、语义同题审核和交叉一致性审核。
3. 工作台增加逐项审批和异常中心。

### P3：稳定自动化

1. 去除项目硬编码和一次性修复逻辑。
2. 建立依赖失效和增量重跑。
3. 完成多个真实项目回放后，再开放无人值守自动续跑。

## 九、建议的下一次调试起点

从第二步“招标解析”重新开始，但只调一个能力：**原子条款拆分和对象归属**。以本项目技术章节为样本，先人工确认一份黄金条款表，再让解析器达到 100% 关键条款覆盖。该能力通过后再进入证据匹配和技术响应，不再直接回放完整十步。
