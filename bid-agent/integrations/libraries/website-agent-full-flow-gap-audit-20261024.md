# 德塔智能招投标系统 Agent 全流程细化审计

审计日期：2026-10-24  
审计对象：网站智能体 `5546cce7-872d-483a-a260-893339fbe05d`、十步项目网关、自动续跑、知识与证据工具、文档生产与质检工具。

## 结论

当前系统已经具备项目隔离、原件哈希、招标原文索引、条款原子化、三库检索、原件页验证、适用性校验、结构化数值比较、八列表生成、文档编辑和视觉单页检查等工具。但“通用十步 Agent”仍未完成。现有十步生成脚本和阶段验证器实际是上一真实项目的专用实现，换项目后仍会按陶忽图项目的固定车型、条款数、证据数、页数、文件名和结论验收。

因此，目前可可靠复用的是底层单项工具；不可可靠复用的是从第 3 步到第 10 步的通用自动生产及验收链。

## P0：会直接导致新项目结果错误或流程中断

1. **十步验证器项目硬编码**
   - 第 4 步固定校验项目编号、采购人、投标人和证书编号。
   - 第 5 步固定 12 个评分项、固定得分和三年利润值。
   - 第 6—8 步固定 327 条技术要求、固定车型及 14 项负偏离。
   - 第 9 步固定陶忽图输出文件名、1000 个槽位、13 份附件和 PDF 三件套。
   - 第 10 步固定 139 页、修改第 100 页、14 项负偏离。
   - 这些常量存在于 `integrations/weknora/project_stages.py`，不能作为新项目的通用门禁。

2. **阶段生成脚本仍是上一项目专用脚本**
   - `build_stage4_qualification.py` 至 `build_stage9_assembly.py` 含陶忽图项目名、WLR-5C(E)、WC5J(A)、GZC2/500、固定证书与固定文件名。
   - 当前不存在由本项目第 2 步结构化结果动态驱动的通用 stage builder。

3. **自动续跑仍绑定旧项目规则**
   - `auto_continue.py` 固定 Workbuddy 模板、V3 工作稿路径、陶忽图输出名和最终 PDF。
   - systemd 单元本身仍命名为 authorized Tao Hu Tu project，并固定旧 session/project。
   - 连续两轮没有新增文件即判 stalled，无法区分长任务、检索任务和真正卡死。
   - 默认最多 16 轮，未按条款数和批次数动态计算工作量。

4. **配置策略相互冲突**
   - 在线提示词仍写“适用对象需人工逐行确认”，同一段又要求机器门禁通过后自动续跑。
   - `policy.json` 仍写 `downstream_allowed=false`、必须用户确认；在线提示词要求无需等待确认。
   - 自动续跑仍要求 PDF 出现在 outputs；在线提示词和当前业务要求只允许 DOCX、DOCX、XLSX，PDF 仅内部检查。

5. **拟供车型“锁定”尚不是可信锁**
   - 偏离工具只检查 `selection_source` 非空、两个字段看起来像 SHA-256。
   - 它没有打开项目选型记录，也没有验证 `source_index_sha256` 对应当前项目真实文件。
   - 模型可以构造形式合法但未绑定真实选型文件的锁定对象。

6. **生产运行环境依赖漂移**
   - `deta-agent-tools.service` 使用 `weknora-mcp-env`；该环境缺少 `docxcompose` 和 `pymupdf/fitz`。
   - 项目 `.venv` 有这两个包，但缺少 `httpx`；技能专用 venv 也缺 `docxcompose`。
   - 依赖清单写有 `docxcompose==2.2.0`，腾讯镜像目前无法安装该版本。
   - 使用项目 `.venv` 执行 117 个测试，111 个通过、6 个错误；使用技能 venv 时有 24 个模块加载错误。

7. **知识索引与备份定时任务已失败**
   - `deta-bid-knowledge-index.service` 与 `deta-bid-daily-backup.service` 均因 `/opt/deta-bid/current/scripts/...` 无执行权限失败。
   - 上一次知识构建日志显示 1991 个图片事实视觉任务全部失败，22 个车型卡均为 `needs_review`，可调用图片事实为 0。

## 横向能力缺口

1. **状态模型未真正落地**：需要分别保存“已执行、结构通过、内容通过、人工批准、可递交”，目前阶段回执把 Agent 验证写成 `semantic_verified=true`，但不少验证仅是固定常量匹配。
2. **语义质检仍是关键词规则**：`check_response_logic` 依赖“尾气净化装置、供货通知单、备品备件”等固定词，不能稳定识别回答跑题或比较对象不一致。
3. **旧矩阵校验未接入新证据链**：`check_requirement_matrix` 会把所有行加入 pending review，未消费原件页验证、适用性、数值关系和锁定选型结论。
4. **报价闭环不足**：只有历史价格恢复和简单一致性工具，缺少本项目审批价导入、税率、数量、单价、合价、总价、大小写与分项汇总的统一门禁。
5. **长任务可恢复性不足**：批量证据工具单批最多 20 条，但没有系统调度器自动分片、落盘、续批、重试和总覆盖核对；当前依赖大模型自行循环调用。
6. **模型运行治理不足**：没有按任务选择对话/视觉模型、失败自动回退、额度/耗时监控和调用审计的统一策略。

## 建议整改顺序

1. 先把 `project_stages.py` 和所有 `build_stage*.py` 去项目化：所有计数、车型、证据、文件名和结论都从当前项目清单派生。
2. 建立可信的 `project-facts.json`、`configuration-lock.json`、`qualification-ledger.json`、`scoring-ledger.json`、`technical-traceability.json` 五个核心账本，并以真实文件哈希互相绑定。
3. 重写自动续跑为数据库任务队列：按阶段和条款批次持久化，不在提示词中写项目文件名，不因两轮无新文件误停。
4. 将第 8 步改为确定性内容门禁，直接消费五个账本，阻止已知字段漏填、跑题响应、无证据结论和跨文件冲突。
5. 最后通用化组装、全页视觉检查和最终放行，只展示 DOCX 投标文件、DOCX 八列表、XLSX 八列表。

下一项应先优化 **“通用项目事实与选型锁”**。这是资格字段自动填写、技术证据适用性和偏离结论共同依赖的基础；不先解决它，后续步骤仍会依赖提示词和伪锁定字段。
