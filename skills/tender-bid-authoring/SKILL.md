# 标书制作 v1.38

## 受保护的制作指导书

多车型分组及本项目车型筛选已并入该手册的第七步和 T08 模板说明；不再维护单独补充章。

手册原件为**受保护的只读依据**，当前登记的 SHA256 为 `32FE1560C7D9CE9AB5B9136D548BD5ADF6666A50A3D2B8843EB82395910F7B28`。制作前核对文件及指纹；缺失或指纹变化时说明实际情况，不擅自用其他版本替代或声称已按该版执行。不得自行修改、重排、覆盖、另存替换或同步改写手册；**只有用户明确要求修改该手册时**，才可在保留原件和变更记录的前提下修改，并重新核对本技能与手册的对应关系。用户要求修改技能、生成标书或修订项目文件，本身均不构成修改手册的授权。

适用顺序：本项目招标文件及有效澄清的强制要求、用户对本项目的明确指示优先；手册指导默认制作方法、格式和检查；本技能及其专项规则负责执行细节。若手册与技能专项规则或项目要求冲突，先记录冲突及依据，不得静默选择方便执行的一方；影响业务含义且无法判断时请求用户确认。手册中的示例项目、车型、数值与模板占位符不能作为当前项目事实。

## 目标与边界

制作用户要求的实际投标文件，不能用分析清单、JSON、空白骨架或检查报告替代成品。招标文件及有效澄清决定强制结构、采购范围和评审条件；真实企业资料、业务确认及适用历史文件决定填写值、响应正文和证明材料。

默认在本地工作。原件、历史成果和人工修改只读保留，修订输出新版本。未经用户授权，不修改线上项目、资料库、权威库或云端配置。历史标书只可提供成熟结构、版式和可复用内容，不得带入旧项目名称、客户、价格、人员、日期、签章或不适用配置。

## 完整制作主线

“先骨架、后填充”是完整制作流程中的结构控制方法，不是新的交付目标。完整制作必须连续完成：

`冻结项目输入 → 解析招标要求 → 生成并冻结空白骨架 → 招标技术原文转横向Excel → 按槽位匹配资料 → 填写商务与资格内容 → 完成内部技术对标Excel与技术方案 → 装入证明附件 → 组装目录和页码 → Office渲染 → 逐页终审 → 交付DOCX及技术对标XLSX`

用户要求“制作标书”时，除非用户明确只要骨架，否则不得在骨架生成、解析完成、资料召回或任一中间阶段停止。骨架、要求矩阵、槽位清单和内部台账均为中间产物；交付物是已填商务及技术正文、适用证明材料的可编辑DOCX，以及另行填写的内部技术对标XLSX。正式DOCX中的详细技术响应表按本次明确指示保留原式且投标人填写区留空；其余应填内容不得因此省略。资料不足时，在真实依据范围内形成候选卷并列出缺项；不得退化为空骨架或编造事实。

完整十步、阶段产物和停止条件先按受保护指导书核对，再见[完整标书制作主流程](references/full-authoring-workflow.md)。所有新建或明确重制项目用`scripts/workflow_engine.py`记录状态、依赖、产物、哈希和失效范围；旧项目记录只读保留。

## 不可违反的制作原则

1. 当前招标文件和有效澄清优先，历史文件仅作参考。冲突无法判断时标记待确认。
2. 不编造企业资质、业绩、人员、产品参数、检测报告、价格、签章或履约承诺。
3. 招标原文、企业事实、历史响应、AI草稿、人工确认和内部检查信息分开管理。
4. 招标明确的表式、固定文字、要求列、编号、列序、合并、签章位和章节顺序不得擅自修改。
5. 骨架原件只读；后续只在冻结槽位中填充副本。需要新增章节、表格或材料位置时回到步骤1重建骨架。
6. 招标原文列逐字保留。模型只能理解和填写响应区，不能改写要求列或用模型结论覆盖Rulebase失败。
7. 业绩表、正式商务偏差表、正式技术偏差表及正式详细技术响应表按本次业务规则保留招标原结构且投标人填写区留空；技术对标在独立XLSX中完成，资格和评分影响另行如实判断。
8. 已知字段必须实填；确实缺少依据的字段保持空白并进入缺项清单。内部“待确认、证明未齐”等提示不得进入正式正文。
9. 每个正式章、节、小节默认另起页，标题与本节首段、首表或首张材料同页；招标明确规定连续排版或固定分页时以招标为准。
10. 模型失败可使用确定性代码生成候选内容和DOCX，但代码无法完成的语义、适用性或视觉判断保持`unresolved`，不得伪装成审核通过。

## 完成状态

严格区分以下状态：

- **骨架完成**：仅说明结构和格式已冻结，不能称为标书完成。
- **候选稿完成**：商务、技术正文和适用附件已装配，内部技术对标XLSX已形成且真实缺项已列明，可供人工审核或下载。正式详细技术响应表按本次指示留空，若招标强制填妥，该状态不能升级为可递交。
- **文件制作完成**：DOCX结构、目录、页码、渲染及逐页检查已完成，但仍可能有报价、签章或业务批准事项。
- **可正式递交**：十步均为当前有效的`passed`，逐页覆盖率100%，`delivery_decision=ready`且`qualification=met`。

仅有标题、空表、通用占位响应、无正文或未装入已选证明附件的文件，不得标记为候选稿、制作完成或交付成功。下载和预览使用真实DOCX/PDF；JSON只作为内部状态和清单。

## Rulebase与Agent

- `R`负责输入哈希、字段、结构、表格、附件、页码、槽位权限、版本和门禁，使用版本化代码保存可复查结果。
- `A`负责评分与条款语义、材料适用性、开放性正文、客户化改写和逐页视觉判断，必须收到原文及位置、任务边界、锁定项和结构化输出契约。
- 混合任务按`R固定输入与边界 → A理解或生成 → R回验 → A视觉或语义复核`执行。模型不可用时走代码兜底并把Agent结果记为`candidate`，附`execution_mode`和`open_items`；下游可继续生成候选文件，但正式交付门禁要求所有阶段最终为`passed`。

任务包按[Agent阶段任务契约](references/agent-task-contract.md)组织；确定性脚本、命令及能力边界见[工具契约](references/tools.md)。

## 交付前最低检查

- 招标要求、评分项、资格、否决项、响应性条款与最终章节逐项对应。
- 已知字段实填；业务指定留空表仍保持原结构且填写区为空。
- 招标技术要求逐行进入独立XLSX，原文、编号和顺序未变；正式DOCX的详细技术响应填写区按本次指示留空。内部拟应答与报告现值、差异和证据同一行可核，未确认目标不得写成实测达标；不另交技术偏离清单。
- 多车型技术要求在独立XLSX中沿用招标原本的合写或分写结构；前三栏为模块映射，标准答案列仅包含本项目招标车型及其报告锁定子型号，随后才是本项目要求、响应和偏离。逐项复核“原要求—模块—同报告标准答案”是否同行且语义相同；招标未要求的模块不填项目应答，缺标准值留空。不得把长期横向总表中无关车型带入本项目，也不得把这些分析列加进正式DOCX空白技术表。
- 已采用证书、报告、图片和证明材料实际进入指定附件位置，正文引用可反查原件。
- 无旧客户、旧项目、旧车型、历史价格、调试文字或未替换占位符。
- DOCX可打开，目录页码来自最终渲染，表格和图片无裁切，章节分页符合本项目规则。
- 最终页图逐页检查并记录；修改后重渲染变化页及受分页影响的页面。

最终只交付用户要求的文件。内部分析、复用台账、缺项、规则结果和逐页记录保存在项目工作目录；报告中分别说明“文件已生成”“仍有业务未决”和“是否具备正式递交条件”。
