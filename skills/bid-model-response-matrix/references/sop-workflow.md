# SOP：车型标准响应参考表

一句话：**把招标技术条款逐条摊开，一条一行，用同车型历史响应回答，逐条给出可核查的偏离结论；原文次序、原文编号、原文语序都不动。**

最终交付物是「按招标要求逐项输出的完整技术响应表」。拆分模块、匹配历史、记录来源，都只是**找答案的手段**；手段的产物（中间 JSON）用于核查答案是否找对、是否规范，默认不放进交付表。

---

## Step 0 前置点收

| 输入 | 要求 |
|---|---|
| 招标技术部分原件 | PDF / DOCX，优先拿原始排版文件；扫描件先做 OCR 并人工校对编号 |
| 历史同车型投标文件 | 至少 1 份同平台/同型号族的投标技术响应，含参数表与技术条款答复 |
| 产品资料与证明材料 | 安标证、防爆合格证、检验报告、型式试验报告（用于正偏离与数值类应答） |
| 业务改写稿（可选） | 标蓝/批注版本，代表业务已确认的口径，优先级最高 |

开工前必须确认三件事，否则后面全是返工：

1. **同车型怎么算**——同平台改进型（如 WLR-5 → WLR-5C(E)）算，跨车型（指挥车 → 升降车）不算。
2. **车型清单**——每个车型一段参数表还是一张合表；合表要拆成行并标注车型。
3. **交付形态**——默认只出主表；过程数据留在工作目录。若业务要求核查页，另出一个 sheet，但不得混入主表列。

---

## Step 1 抽取招标要求（逐字、按序）

```bash
python scripts/pdf_table_dump.py 招标技术部分.pdf -o tables.json
python scripts/pdf_text_dump.py  招标技术部分.pdf -o tender_text.txt
```

- 表格：`pdf_table_dump.py` 已按三条件拼接跨页续表（见 `numbering-rules.md`）。
- 正文：按章节标题正则切分，每节标 `kind: table | para`；段落保留原文编号 `no`（`（1）` / `1、` / 空）。
- 表格行保留 `no`（原文行号）与 `cells`（原文各列），不要提前拼成一句话——拼接在出表时做。

**硬要求**

- 不改写、不概括、不合并同义条款、不删除"重复"条目。
- 剔除页码与页眉；PDF 断行不得改变语序，中文行与行直接相接。
- 表格单元格内的换行按原文保留为空格或顿号，不得丢字。

**四个真实踩过的坑**

| 坑 | 现象 | 处理 |
|---|---|---|
| 标题恰等于正文 | 整条被当成重复而丢失（6.2.11/13/16） | 标题与正文分开存；相等时正文照留 |
| 标题在 PDF 句中断行 | 前半句成了"功能模块"，后半句成了"要求" | 标题取短名，正文还原完整句 |
| 条款正文是上一句的续行 | 无编号段落被吞进上一条 | 按句号与版式切分；无编号即独立成条 |
| 续表被当成新表 | 行号又从 1 开始，后表覆盖前表 | 三条件判定续表；不满足即视为新表 |

**出口** `requirements.json`（schema 见 `data-schema.md`）。**验收**：每条要求正文都能在 `tender_text.txt` 中命中（Gate D）。

---

## Step 2 拆模块（只标注，不排序）

维度固定四层：**车型 → 子系统 → 部件 → 功能**。

- 功能名优先用原文行名或条款题名；原文没有短名时才归纳（如"电源和电源管理系统"）。
- 一个原文条款只挂一个功能；跨模块条款按"要求主体"归类，不按车型归类。
- **行序 = 招标原文节序**。任何"按车型归并""按模块重排"都会破坏可核对性，禁止。

**出口** `module_dict.json`，并打印子系统/部件/功能计数，供人工确认粒度合理（一般 8–15 子系统、20–35 部件、60–90 功能）。

---

## Step 3 拆历史模板（同一套词表）

把历史投标文件里的响应表按同样四层切开，每条保留：

`project｜model｜doc｜table｜row｜param（参数名）｜req（历史要求原文）｜resp（历史响应原文）｜dev（历史偏离）`

- `param` 取历史行"名称"列冒号前的部分；没有名称列的，用原文前 12 字。
- 归类用与 Step 2 相同的词表；归不进的进"其他"，不影响匹配结论。
- **来源三元组必须完整**，否则这条历史答案不可引用。

**出口** `history.json`。

---

## Step 4 逐条对应

```bash
python scripts/match_history.py --req requirements.json --hist history.json \
  --alias assets/alias-example.json --hints assets/hints-example.json \
  --same-model WLR-5 -o match.json
```

五级匹配见 `matching-rules.md`。要点：

- **只允许同车型取答案**；无同车型模板的车型，全部判"无历史"，响应由业务/产品资料填。
- 找不到就写"无历史"，**不许靠关键词模糊搜索凑来源**——"总电压"曾被匹配到"监控项目"，这类错误比空白危险得多。
- 段落条款的历史命中只能作"关键词参照"（旁证），不能当答案。

**出口** `match.json`（每条带 match_type / source / confidence）。**人工复核**：随机抽 10 条，确认"历史参数名 → 历史响应"真的回答了本条要求。

---

## Step 5 组装响应

响应取值优先级：

1. 业务已确认改写（标蓝稿 / 技术部答复）
2. 同车型历史响应原文
3. 产品资料 / 证书 / 检验报告中的实测值
4. 空（标"待确认"，不编）

偏离与措辞按 `deviation-and-wording.md`；编号按 `numbering-rules.md`。

```bash
python scripts/build_matrix_xlsx.py matrix-spec.json -o 交付/车型标准响应参考表.xlsx --strict
```

构建器会强制执行：编号嵌入两列行首、无偏离剥离说明、去"已满足"、模块列合并、正偏离必须有优于说明。

**每一处业务改写都留一条修订记录**（键 = 条款号#行索引，值 = `why` / `dev` / `resp`）。这样复审时能回答"这句话为什么这么写"，而不是只剩一个结果。

---

## Step 6 双校验

```bash
python scripts/verify_matrix.py 交付/车型标准响应参考表.xlsx \
  --source tender_text.txt --allow-dup 5.3.5,6.2.5 --report chk/校验报告.txt
```

四道门（`qa-checklist.md`）：结构 / 编号 / 偏离语义 / 原文逐字。

**机器过完之后必须人工做两件事**：

1. 数值类条目逐条对证书与检验报告（总能量、续航、功率、尺寸、载重）。
2. 正偏离说明逐条读一遍，问一句"这句话说的是不是本条要求的东西"。

---

## Step 7 交付

- 默认交付**单个 sheet** 的 xlsx（8 列）。过程 JSON、校验报告留在工作目录，按需提供。
- 汇报口径：总条数、偏离分布、无历史条数、待业务确认清单、原文自身的编号异常（重号/无号）。
- 不主动交付中间 PNG/PDF/JSON，除非用户要求核对。

---

## 返工时的最小改动原则

| 反馈类型 | 改哪里 | 不要做什么 |
|---|---|---|
| 某条说明写错主体 | 该条响应文本（修订层） | 不要改招标要求列 |
| 编号不对 | 编号推导规则或原文编号数据 | 不要手工改单元格 |
| 次序不对 | 输出循环顺序 | 不要按车型重排 |
| 偏离判定不对 | 该条 `dev` 与依据 | 不要只改文字不改结论 |
| 招标原文识别错 | Step 1 的 `requirements.json` | 不要在 xlsx 里打补丁 |

改完必须重跑 Gate B/C/D；主表任何一行变化都要能解释来源。
